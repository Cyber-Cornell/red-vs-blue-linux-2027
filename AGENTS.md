# CCDC Linux toolkit contributor guide

This repository is a Linux blue-team toolkit for competition hosts. Keep scored services, remote access, and telemetry working. A read-only audit or plan must be the default for every new host-changing tool; require an explicit apply action and `--yes` before installation, policy changes, service restarts, or account changes. Do not infer authorized accounts, ports, destinations, or service dependencies from examples. Preserve operator configuration, make bounded backups before overwrites, validate native configuration, and provide a rollback path.

Use POSIX `sh` for target scripts where practical. Reuse helpers in `shell/lib/portable.sh` and support both systemd and OpenRC where a service is involved; report unsupported platforms or missing utilities clearly. Keep hunts bounded by time, number of files/processes, output size, and storage. Treat heuristic findings as review leads. Do not print passwords, tokens, command-line secrets, or environment values to general logs. Put sensitive artifacts in private directories with mode 0700 and files with mode 0600. Optional network downloads must use official sources and integrity checks. OpenCode and OMO installation belongs only in the target-side opt-in script, never in setup/check/audit on the development machine.

`shell/setup.sh` is the operator entry point: `check`, `list`, `plan`, `audit`, `hunt`, `backup`, and explicit `apply`. Standalone tools live in `shell/tools/`. Ansible wrappers in `ansible/playbooks/` stage the toolkit in a fresh private per-run directory on target hosts, remove that directory after execution, and invoke the same commands; keep new tools runnable through `tool.yml` even if they are not in a default profile. Avoid adding disruptive stages to the `baseline` or `host` profiles. Service isolation and MAC changes must stay opt-in and must verify the reviewed service's health and logging path.

The default audit and hunt workflows include the observability audit. Connection hunting reserves its 128-row budget for 96 TCP/UDP and 32 packet/raw sockets, and packet/raw owner correlation remains partial. Persistence, process, web, Docker, and package-verification collectors have explicit whole-run deadlines and output caps; process and Docker collectors also cap reviewed objects. These collectors report metadata/hashes or suppressed-value summaries for credential-bearing persistence, source, Docker daemon, event, and audit-command data. SSH and rsyslog audits summarize authentication records and managed log files without printing their message values. The executable Git-hook survey never executes hooks or prints their contents. Gentoo package changes use explicit category/package atoms through guarded `emerge` plans and applies. Keep AppArmor/SELinux changes, prepared-container handoff, systemd sandboxing, ClamAV actions, LinPEAS, YARA, and target-side OpenCode/OMO installation as standalone opt-in tools.

The project-local `incident-response-report` Codex skill lives under `.agents/skills/`. Keep its report guidance evidence-grounded: distinguish observations, assessments, and unknowns; preserve source provenance and time-zone context; and never put real incident evidence in the repository.

Before changing behavior, consult the relevant upstream program documentation and distro guidance, including ArchWiki and Gentoo Wiki when applicable. Update `README.md`, `docs/VALIDATION_MATRIX.md`, and this file whenever commands, defaults, supported distros/init systems, safety bounds, telemetry paths, or validation claims change. The LinPEAS compatibility path is the SHA-256-verified upstream runner; document its pinned release and distinguish upstream execution from checks implemented locally.

Validate syntax with `sh -n` on target scripts and `ansible-playbook --syntax-check` on playbooks. Run applicable behavior in the cached Alpine Docker image with the repository mounted read-only, a small tmpfs, memory and CPU limits, and no extra image pull. Use fixtures/adapters for state-changing commands, plus native utilities where safe. Do not install product software or change services on the development machine during tests. Record what was actually observed and what remains untested. Preserve LF endings on shell/config/YAML files so Linux execution works after a Windows checkout.

Do not push. The current user authorized one local commit after validation; do not include `.omo/` evidence, secrets, downloaded scanners, temporary reports, or `node_modules/` in it.
